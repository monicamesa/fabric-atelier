# Lessons learned building Fabric Apps

Gotchas we hit while building Agent Jury (a Fabric App on the Rayfin CLI 1.36.2, Windows, PowerShell 5.1, with Fabric Data Agents as the thing being evaluated). Fabric Apps, the Rayfin CLI, Data Agents and the evaluation SDK are all in **preview**: some of this will go stale. Each lesson has a symptom, the cause, what we did, and where to read more. Dates are 2026-11.

No tenant, workspace, item or capacity identifiers, emails or URLs appear here, by design (see [conventions.md](conventions.md)).

> **Rule for contributors, human or agent:** when you hit a new gotcha, add it here in the **same commit as the fix**. Keep the four-part format and link the doc or commit. Do not put private values in it.

Paths below are relative to this file. `I1a`, `I1b`, `I1c` and `I3` are the iteration docs in [apps/agent-jury/docs/iteraciones/](../apps/agent-jury/docs/iteraciones/) (in Spanish); [estado.md](../apps/agent-jury/docs/iteraciones/estado.md) is the project status.

## 1. Environment setup

### PowerShell blocks `npm` and `npx`
- **Symptom:** "running scripts is disabled on this system" for `npm.ps1` / `npx.ps1`.
- **Cause:** the default execution policy blocks the `.ps1` shims.
- **What we did:** always call `npm.cmd` and `npx.cmd` (or relax the policy for the current user).
- **More:** [estado.md](../apps/agent-jury/docs/iteraciones/estado.md) ("Problemas conocidos del entorno"), [AGENTS.md](../apps/agent-jury/AGENTS.md) ("Verified working notes").

### nvm-windows breaks on a user path with accents
- **Symptom:** `nvm root` fails with "could not be found" and rewriting `settings.txt` drops the Node link.
- **Cause:** nvm-windows does not support non-ASCII characters in its install path.
- **What we did:** uninstalled it and installed Node 24 with winget, pinned to `24.*` (`winget pin add`) so an upgrade cannot jump a major version. Install tools outside the user folder when you can choose.
- **More:** [estado.md](../apps/agent-jury/docs/iteraciones/estado.md) (decisions), [conventions.md](conventions.md) ("Requirements").

### winget installs that need admin fail silently from the VS Code terminal
- **Symptom:** exit code 1602 ("user cancelled").
- **Cause:** the UAC prompt never appears in the integrated terminal.
- **What we did:** run the install from a PowerShell opened as administrator outside VS Code.

### The integrated terminal sometimes returns nothing
- **Symptom:** a command runs but no output comes back, so it gets repeated.
- **Cause:** the terminal capture stalls. We also saw it after a duplicated `npm ci` (`ENOTEMPTY`, then `EPERM` on `node_modules`).
- **What we did:** run long commands once, async, write to a UTF-8 file under `.private/` and read the file. `Out-File` buffers until the command ends, and without `-Encoding utf8` it writes UTF-16. Scripts must call `process.exit`, or they hang when piped. Before repeating an npm command check for stray `node` processes.
- **More:** [estado.md](../apps/agent-jury/docs/iteraciones/estado.md), [AGENTS.md](../apps/agent-jury/AGENTS.md).

### `npx <tool>` can swallow the next command
- **Symptom:** a script never ran, and the next command's output looked stale.
- **Cause:** `npx` of a package that is not installed (we tried `vite-node`) waits for "Ok to proceed? (y)" in that shell.
- **What we did:** use what is installed (a temporary `vitest` spec ran the TypeScript rules in Node) and never `npx` an uninstalled tool in a shared terminal.

### `rayfin up` edits `rayfin.yml`
- **Symptom:** after every deploy `rayfin.yml` has a new entry in `allowedRedirectUris` with the deployed app URL, which you must not commit.
- **Cause:** the CLI registers the app URL so sign-in works.
- **What we did:** commit first, deploy with the full `rayfin up` (never `--exclude-services staticHosting`, which skips the URL registration), then `git restore rayfin/rayfin.yml`. Our deploy script does it for the test deployment.
- **More:** [conventions.md](conventions.md) ("`rayfin.yml` after a deploy").

### Function types are not regenerated by `rayfin up`
- **Symptom:** a new Function is missing from `types.ts`, so typed client calls fail.
- **Cause:** typegen only runs with `rayfin functions init` (without `--force`) or `rayfin dev functions apply`.
- **What we did:** run `npx rayfin functions init` after changing a `udf.func()` signature, before the deploy.

### `TS6377` from the root project reference
- **Symptom:** the root `tsc -b` fails because of `rayfin/`.
- **Cause:** `rayfin/tsconfig.json` shares a build-info file with the root project.
- **What we did:** give `rayfin/tsconfig.json` its own `tsBuildInfoFile`.

### A second deployment for testing
- **Symptom:** deployed checks and seed data polluted the real app.
- **What we did:** a separate workspace and app item for tests (`scripts/deploy-test.mjs` deploys there, writes a git-ignored env file and switches back to production). Check scripts default to the test deployment and need `--target=production --allow-production`; seed SQL marked `-- target: test-only` refuses production. The CLI has no top-level `switch`: it is `rayfin up switch`.
- **More:** I1c section 2, [README](../apps/agent-jury/README.md) ("Test deployment"), commit `ec89160`.

### Private values: keep them out of Git without rewriting history
- **Symptom:** tenant, workspace and item IDs, emails and app URLs creeping into docs and tests.
- **What we did:** one git-ignored `.private/values.env`, referenced by key name in tracked files, plus a pre-commit hook that blocks those values, GUIDs outside `00000000-0000-4000-8000-0000000000NN`, non-`example.com` emails, deployed URLs and Windows user paths. The hook also caught a made-up GUID in a test fixture (use a plain string). We chose not to rewrite earlier history.
- **More:** [conventions.md](conventions.md) ("Private values"), commit `ec0b63d`.

### Scripts that sign in as the user
- **Symptom:** `az account get-access-token` cannot get the `Item.Execute.All` scope that the app sign-in exchange needs.
- **Cause:** Entra refuses that scope for the Azure CLI client.
- **What we did:** use `getAuthenticatedToken` from `@microsoft/rayfin-cli/auth` and `signInWithEntraToken`, which needs `services.auth.fabric.externalEntraExchange: true`. Enable it only while running checks.
- **More:** [conventions.md](conventions.md) ("Sign-in from scripts"), I1a section 6.

## 2. Identity and security

### A Function does not know who called it
- **Symptom:** `ctx.accessToken` has no `email`, and its `sub` is not the signed-in user.
- **Cause:** it is a Fabric platform token (`idtyp: fmi`), not the Rayfin token of the caller.
- **What we did:** the browser inserts an `AdminRequest` row (the insert policy proves `claims.email`), then calls `clerkExecute(requestId)` with only the id. The Function reads the row with T-SQL under the app identity and checks admin, age (2 minutes) and single use, and writes the result in the same transaction.
- **More:** I1a section 6 ("Seguimiento: identidad de admin"), [spec section 7](../apps/agent-jury/docs/especificacion-general.md), commit `a2063d1`.

### Function names starting with `admin` or `runtime` never run
- **Symptom:** every call returns `WorkloadException / NotFound ... invocation failed`, without reaching your code.
- **Cause:** the Azure Functions host reserves those routes. Ten diagnostic Functions in other shapes all worked, which left the name as the only difference.
- **What we did:** call it `clerkExecute`. Entities and tables may keep the `Admin` prefix.
- **More:** I1a section 6, AGENTS.md rule 24.

### A deleted Function does not say "not found"
- **Symptom:** after removing a Function it answers "Application authentication for this function is currently unavailable".
- **What we did:** treat that message as "gone" only after a known-good Function still answers in the same deployment (we re-ran the deployed checks of `clerkExecute` once: all passed, so Functions auth was fine and only the spike was gone). Verify removals by invoking the Function once after the redeploy. A Function you leave deployed stays callable, so remove throwaway spike Functions and redeploy the same day.
- **More:** I1a section 6, I3 section 15.

### Two identities in one Function
- **Cause:** `ctx.Tokens.*` (SQL, Fabric, Storage...) use the **app identity, which today is the owner of the app item**. `ctx.getDataClient()` uses the **caller's** Rayfin token and permissions.
- **What we did:** privileged reads and writes use T-SQL with `ctx.Tokens.Sql`; restrictions are enforced in the code that runs under that identity, not by the client.
- **More:** [Functions in Fabric Apps](https://learn.microsoft.com/fabric/apps/functions) (Microsoft Learn), I3 section 2.

### Insert policies are enforced, including `claims.email`
- **Symptom (worry):** the Data API Builder docs say database policies do not apply to `create`.
- **What we did:** a negative test against the deployed app: inserting a row with someone else's `authorUserId` or `authorEmail` is rejected ("Could not insert row with given values"). We keep this as a deployed check, not an assumption.
- **More:** I1a section 6 (R1).

### The client is not an authorization boundary
- **What we did:** domain records are insert-only with an owner field, `Juror` and `Agent` are read-only for the client and written only through the admin Function, and case state (ruled, disputed...) is **computed from the records, never written**, by one shared, tested module.
- **More:** [AGENTS.md](../apps/agent-jury/AGENTS.md) rules 15-21, [spec section 6](../apps/agent-jury/docs/especificacion-general.md).

### Dates set by the client can be forged
- **Symptom:** a client could date a vote in the future so it is always the latest.
- **Cause:** Rayfin cannot generate `createdAt` on the server (the `@date` default is a fixed value).
- **What we did:** the rules ignore records dated more than 5 minutes in the future and the court record flags them. Documented as a known risk.
- **More:** [spec section 6](../apps/agent-jury/docs/especificacion-general.md).

### A notebook run by an API call runs as a person, with all that person's rights
- **Symptom (risk):** the evaluation notebook runs as the app owner and could change anything in the app database.
- **What we did:** the notebook may only read two tables and `INSERT` into two others: no DDL, no scratch tables, no `UPDATE` or `DELETE`. A static check (`scripts/notebook-sql-policy.mjs`) and its tests fail the build if any real notebook breaks that. It is a source check, not a database barrier; a least-privilege identity is still open.
- **More:** I3 section 15, commit `4232c7e`.

## 3. Data model and policies

### Text foreign keys are rejected
- **Symptom:** the CLI refuses a model that follows the Learn example with `@text({ max: 36 })` for a foreign key.
- **What we did:** declare foreign keys as `@uuid()` named `{property}_id`, paired with `@one()` / `@many()`. No many-to-many.
- **More:** [AGENTS.md](../apps/agent-jury/AGENTS.md) rule 12.

### A text field with no `max` becomes `NVARCHAR(MAX)`
- **Symptom:** GraphQL metadata generation can break.
- **What we did:** give every text field an explicit `max`.
- **More:** AGENTS.md rule 11.

### Policies only compare claims with the row
- **Symptom:** you cannot write "the voter is an approver" or "the author is an active juror" as a policy.
- **Cause:** `@role` policies compare `sub`, `email` or `role` with a field of the same row using `.eq()`. They cannot query another table.
- **What we did:** the policy proves identity only (`claims.sub.eq(item.voterUserId)`); validity (active juror, role, no self-approval) is computed when the state is derived.
- **More:** [spec sections 4 and 7](../apps/agent-jury/docs/especificacion-general.md).

### Rayfin names and types
- **Facts:** tables are pluralized (`dbo.Jurors`, `dbo.Cases`); `id` is `uniqueidentifier` with `newid()`; the Fabric `serverFqdn` is `host,1433` and the `mssql` driver needs host and port apart; `findById()` returns only `id` (use `select([...]).where({ id: { eq } })`); there are no hidden system columns, so T-SQL inserts show up correctly through the API.
- **More:** I1a section 6 (S-B results), [AGENTS.md](../apps/agent-jury/AGENTS.md).

### Validation failures come back as a generic error
- **Symptom:** a too-long text or a bad enum value gives "Internal server error" or "Could not insert row", not a field message.
- **What we did:** validate in the UI and map server codes to plain language, with the technical detail folded away. Deployed checks assert the rejection, not the message.
- **More:** I1b section 9, I1c section 11.

### Never delete: add a record instead
- **What we did:** votes, testimonies and dismissals are insert-only. A vote is changed by a newer vote (the latest counts), a case is withdrawn by a `CaseDismissal`. Check data (`[I1c check]`) stays and is shown as dismissed on the test deployment.
- **More:** [AGENTS.md](../apps/agent-jury/AGENTS.md) rules 15-16 and 23.

### Admin-log noise from check scripts
- **Symptom:** the admin log filled with rows from our own checks.
- **What we did:** scripts mark their requests (`source: "check"`) and the server flags them as automated only when the sender is an active admin, so nobody can hide their own rejected attempts by adding the marker. A cutoff date for older rows is an optional secret, not code.
- **More:** I1b sections 10-11.

## 4. Capacity and cost

### Every request takes exactly 20 seconds
- **Symptom:** all calls (reads, token exchange, even a rejected 401) took 20.1-20.5 s, from curl too; the app took ~82 s to load.
- **Cause:** Fabric's first throttling stage, "interactive delay": once a capacity has used up the next 10 minutes of CU, each new interactive operation waits 20 s. Production and test apps share the capacity.
- **What we did:** paused and resumed the capacity, then checked Capacity Metrics ("Interactive delay") before debugging anything else. We also cut the load from four sequential rounds to one parallel round (1.5 s afterwards), and wrote usage rules: run deployed checks and screenshots once, never poll, never leave a script or dev server pointed at a deployed app unattended.
- **More:** I1c section 11, [conventions.md](conventions.md) ("Capacity usage"), commit `4378b5a`.

### Fewer, parallel round trips beat clever caching
- **Cause:** a screen waited for jurors, then cases, then testimonies, then votes.
- **What we did:** fetch everything in one parallel round and scope it to the agent in the client. Fine for MVP volumes; a nested query or view is the fix when votes reach the thousands.
- **More:** I1c section 11.

### The test database pauses
- **Symptom:** the first T-SQL connection of the day times out.
- **What we did:** retry once.

### Measure the cost per question; do not trust the quoted number
- **Symptom:** the plan assumed ~50 s of agent time per question (the figure quoted by a community project).
- **Cause:** that was not our agent. We measured 12-18 s per question on our agent (about 18 s on average), and an extra 5-8 s of overhead for each call when asking one question per batch.
- **What we did:** use the measured number in the cost estimate and keep a cap per run (10 questions, 5 while building) and one run at a time across the whole capacity. CU consumption is read from Capacity Metrics by hand; scripts cannot read it.
- **More:** I3 sections 8 and 14, commit `04d6b39`.

### Confirm the capacity is healthy before each spike
- **What we did:** a standing rule: the owner confirms "no throttling" in Capacity Metrics before any spike that calls an agent or a notebook; each spike runs once.
- **More:** I3 section 8.

## 5. Data Agents and evaluation

### Evaluation from a plain Python notebook works
- **Facts (SDK 0.1.36a0, preview):** `fabric-data-agent-sdk` installs with `%pip` in a Python notebook with no Spark session (1 core, ~2 min for the whole job). `evaluate_data_agent(df, agent_name, workspace_name=..., table_name=..., data_agent_stage=...)` takes the agent and workspace **by name**. It writes one row per question to the notebook's default Lakehouse: `question`, `expected_answer`, `actual_answer`, `evaluation_judgement` (bool), `evaluation_message` (Yes/No), `execution_time_sec`, thread links, and the agent's version, etag and last-updated time.
- **What we did:** map Yes to correct, No to incorrect and anything else to unclear, and store the raw message and the agent version and etag with every verdict.
- **More:** I3 sections 14-15, commit `04d6b39`.

### The same agent can answer differently over time
- **Symptom:** a draft test gave one answer and, an hour later, the published agent gave the correct one for the same question.
- **Cause:** non-determinism or draft versus published; we could not tell. The SDK reported `enable_preview_runtime=False` while the publish dialog suggested otherwise.
- **What we did:** keep the case as a valid "correct" outcome, record the agent version and etag per verdict, treat the SDK's runtime flag as the truth, and list "answer stability across repeated questions" as a post-MVP idea.
- **More:** I3 section 14, [estado.md](../apps/agent-jury/docs/iteraciones/estado.md).

### Expected answers must come from the model, not from memory
- **What we did:** computed each expected answer with a DAX query against the semantic model and put the DAX in the testimony's definition. The model's own "average order value" measure turned out to be gross, not net: a trap the agent fell into, and a reason to write the definition down.
- **More:** I3 section 14.

### Querying the model from a script
- **Facts:** the Power BI `executeQueries` endpoint rejects `INFO.MEASURES()` and friends but accepts `INFO.VIEW.*`; measure expressions come back empty, so list names and verify values with `EVALUATE ROW(...)`.

### Identity for agents and notebooks
- **Facts:** Data Agents accept a user identity; service-principal support is in preview (needs the tenant setting, workspace role and read access on each source, and does not cover KQL sources); managed identities are not supported. A notebook started through the Job Scheduler API runs as the caller. A Function with the Fabric audience can start it as the app identity (the item owner).
- **What we did:** launch the notebook from a Function and run the evaluation as the owner. Evaluation thread links are visible only to whoever ran the evaluation, so the app does not show them to others.
- **More:** I3 sections 2 and 15 (S3, S4), [Use service principal authentication with Fabric data agent](https://learn.microsoft.com/fabric/data-science/data-agent-service-principal).

### A notebook can reach the app database
- **Facts:** `notebookutils.credentials.getToken("https://database.windows.net/")` plus ODBC Driver 18 (already present) connects to the app's SQL database in about a second, as the running identity.
- **What we did:** pass the server and database as run parameters from the Function; the notebook stores neither.
- **More:** I3 section 15 (S5).

### A third-party "quality lab" is not a standard
- **What we did:** we export the approved bank as a CSV with `question, expected_answer, category, tags`, which a community project (not Microsoft) also reads. Our own test defines the format; loading it there is an optional manual check.
- **More:** I3 section 7.

## 6. Design and UX

### Write a design guide with tokens first
- **What we did:** a short guide with a metaphor, colour tokens for light and dark, type roles and states; only token variables in code (never hex), fonts bundled from npm (no Google Fonts at runtime), and mockups used as visual reference only. Mockup-tool placeholders (`{{ }}`, custom tags) must never be copied into the app.
- **More:** [design-guide.md](../apps/agent-jury/docs/design/design-guide.md), AGENTS.md rules 27-30.

### A highlight that is faint on desktop
- **Symptom:** the rows of the definition-diff table that differ were hard to see on a wide screen.
- **What we did:** a 3 px coral left border, a "≠" marker with an accessible label, and a stronger light-mode background; colour is never the only signal.
- **More:** I1c section 11, commit `4378b5a`.

### Sample IDs make every case number `#0000`
- **Cause:** test IDs all start with the same zeros (the hook only allows that shape) and the number was taken from the start of the id.
- **What we did:** use the last four characters.

### Do not invite more than you can deliver
- **What we did:** the home ticker shows verdict events only (never "new case"), helper lines on phones can wrap to two lines, and the judge-trust block is a single compact line until there are real numbers. Empty and error states say what is missing and never show invented data.
- **More:** I1c section 11, design guide section 6.

### Keyboard focus and what jsdom cannot test
- **Symptom:** focus rings after mouse clicks.
- **What we did:** exactly `:focus:not(:focus-visible) { outline: none; }` plus a `:focus-visible` ring; a spec checks the CSS, and the keyboard behaviour is checked once in a real browser, because jsdom cannot tell keyboard focus from mouse focus.
- **More:** I1b section 11.

### Responsive tables
- **Symptom:** screen-reader-only labels escaped a scrolling container and widened the page on phones.
- **What we did:** hide columns by breakpoint, switch to cards under 640 px (one view rendered, chosen with `useMediaQuery`), and check horizontal overflow in screenshots for every screen and theme.
- **More:** I1b sections 9-10.

### Two languages from day one
- **What we did:** all visible text from locale files (a test asserts both files have the same keys), dates and numbers by language, user-written content never translated, and a glossary check when a word changes (the Spanish "archivar" became "desestimar" everywhere).
- **More:** I1c section 11, AGENTS.md rules 6-9.

## 7. Working with a coding agent

### Put the rules where the agent reads them
- **What we did:** project rules and "verified working notes" live in `AGENTS.md` and `conventions.md` in the repo, not in a chat or a private memory, so a new session (or a new GitHub account) starts with them. `estado.md` records where the project stands and what comes next.
- **More:** [AGENTS.md](../apps/agent-jury/AGENTS.md), commit `ec89160`.

### Plan, review, then build; spikes before screens
- **What we did:** every iteration has a plan with numbered decisions (D1, D2...) reviewed before code. Risky assumptions (identity, notebook launch, database access) are spikes that run once, on the test deployment, and stop for review before any screen is built.
- **More:** I3 sections 9 and 13.

### Token and capacity discipline
- **What we did:** never poll in loops; run a long command once, redirect to a file, read only the summary lines; do not re-run deployed checks or screenshots unless the change requires it; never paste full logs; when waiting is unavoidable, stop and say so.
- **More:** [AGENTS.md](../apps/agent-jury/AGENTS.md) ("Token and capacity discipline").

### File and terminal results can lag
- **Symptom:** a search or a file read shows the old content right after an edit, or an output file is "missing" right after the command ran.
- **What we did:** read the file again before trusting a failure; for edits to the same file, re-check the final content.

### Shell quoting bites
- **Symptoms:** a here-string with `\u00e1` writes the escape literally (type the characters); PowerShell strips the quotes of a JSON argument passed to `node` (use `key=value` pairs); `Move-Item` over a file open in the editor left an empty file (write the final path directly).

### Tool defaults you must override
- **What we did:** `npx prettier` is not installed and prompts, so lint with `npm run lint`; helpers must live outside component files or the `react-refresh` rule warns; a temporary spec left in a folder that vitest scans will run with the suite (delete it after use).

### Ask for confirmation at the gates that cost money
- **What we did:** the owner confirms the capacity before each spike; after that confirmation was relaxed, the stop conditions were explicit (stop if a run takes more than twice the expected time or fails with a capacity or throttling error).

## 8. Limits of Fabric Apps

Things that shaped the design as of this writing:

- **Preview everywhere.** Fabric Apps, the Rayfin CLI, Data Agents and the evaluation SDK change quickly. Pin the CLI and SDK versions and re-check the docs before relying on a detail here.
- **Policies cannot look at other tables**, so roles and "is this person on the list" cannot be policies; use identity-proving policies plus computed validity, and admin Functions for privileged writes.
- **No server-generated dates** for entities (client `createdAt`; see section 2).
- **No many-to-many** relations and no text foreign keys; every text field needs a `max`.
- **A Function does not receive the caller's identity** in its token; prove identity with an inserted row (section 2). Function names cannot start with `admin` or `runtime`.
- **The app identity is the item owner.** External connections from a Function use the owner's rights, so a Function is a privileged door and must enforce its own rules. Changing the owner changes what works.
- **Function limit of 240 seconds.** A Function must start long work (a notebook job) and return; status is read later, not awaited.
- **Capacity is shared.** The app, its test copy and the agent run on one capacity; throttling affects all of them (section 4).
- **Generic server errors** for validation failures (section 3).
- **Local Power BI files are not supported** as a semantic-model source; only published models.
- **Bundle size.** The template's main bundle is over the default 500 kB warning; split screens with dynamic `import()` once there are several.
- **Template dependency audit.** The template ships deprecated packages and `npm audit` findings; review before making a repository public (`npm audit --omit=dev` shows the ones that reach the deployed app).
- **More:** [conventions.md](conventions.md) ("Pending"), [spec section 10](../apps/agent-jury/docs/especificacion-general.md).
